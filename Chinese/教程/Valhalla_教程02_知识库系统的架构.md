## 知识库系统的架构

### 架构概览

知识库系统尽管完全由一个root文件夹建构，但Valhalla还是根据知识的特点构建了一个五层架构：

| 五层架构 |
| --- |
| 图谱层 |
| 关系层 |
| 实体层/知识点层 |
| 资源层 |
| 文件层 |

各层逐层提供服务、逐层封装实现。

上层通过层间接口使用下层提供的能力，而下层不需要知道上层服务的具体实现。

通过这种分层结构，Valhalla 将底层文件组织、资料身份管理、知识实体抽取、实体关系建模和图谱视图构建解耦，从而提高系统的稳定性、可维护性和可扩展性。

### 各层功能

1. `文件层`：这一层构建于root下的Library文件夹，用于放置原始资料。

    由于该层是知识库系统五层架构中的基础，因此没有在Valhalla中设置对这一层的修改操作。

    后续教程中可以看到，Valhalla系统非常容易制作使用者需要的操作(我将它定义为`系统服务`)，但我强烈不建议你制作针对这一层的修改类操作。

    `Library`文件夹中的`public_resources`子文件夹，是一个资源层操作中用于存放原始资料的副本的文件夹，使用者不要修改这个文件夹，后续会解释它的用途。

    除`public_resources`之外，使用者可以在`Library`文件夹中按照自己的需要组织文件夹结构。

    例如：不同领域的资料分放在不同的文件夹中，如果决定多人使用同一个Valhalla系统，不同的使用者可以在Library中建立自己的文件夹，在自己的文件夹中建立自己的资料体系。

    当前只是测试原型阶段，多人协作时需要轮流使用，预计后续很快会发布专门用于团队作业的Valhalla系统。

2. `资源层`：这一层主要用于对文件层的原始资料进行组织。

    文件层的原始资料可能存在`不同路径下的文件重复`、`不同格式`、`同一文件不同名称`等问题，对于上层操作非常不友好。

    因此设置资源层，将文件层的原始文件组织成的`资源`，以便上层调用。

    例如：

    同一篇论文`a`，有pdf版本的，有word版本的，而且各版本的命名还可能不同，导致`aaa.pdf`和`ddef.doc`实际上是一篇论文。

    直接调用原始文件的话会造成不可控的混乱，资源层的作用，则是将`aaa.pdf`和`ddef.doc`组织成一个`资源`，用唯一的`resource_id`表示。

    可以通过root文件夹下的`resource_registry.md`查看。

3. `实体层/知识点层`：这一层用于存储从资源层中的`资源`中提取的`知识点`。

    原始资料文件并不能帮上你，知识才行，就像你买了很多书放在书架上并不能让你增长知识，把它们看完并理解其中的观点才行。

    知识点，我称之为`实体`、`知识实体`、`entity`。

    一个事实是：**一份资料文件中可能包含多个`实体`。同一个`实体`又可能来自多份资料。**

    这使得`实体`和`资源`之间形成了一张关系网，如果没有`实体层`，让更上层直接调用资源的话，会引起极大混乱。

    实体层的作用就是给予一个知识点唯一的`entity_id`，以供上层调用，它被登记在`entity_registry`上。

    `entity_registry`主要记录了实体的缩略内容、源自哪些`资源`、`content_file`链接。

    `content_file`是对该实体的内容的较详细描述，这避免了每次都去重新翻阅所有的`资源`。

    可以通过查看`entity_registry.md`了解实体层，该文件存放在root文件夹下的`Wiki`子文件夹下的某个知识库文件夹(`Wiki_<知识库名>`)下的`.registry/human/`文件夹里。

    这里可以看出，实体层内部其实已经按照知识库的范围进行了划分，后面会详细讲述这一机制，这里只需要有一个笼统的概念即可。

    如此划分主要原因是前面所说的“`实体`和`资源`之间形成了一张关系网”，网络的复杂度是几何增长的，如果对整个`资源层`统一提取实体的话，这个工程量实在太大。因此每个知识库会使用一个叫做`虚拟资源库`的机制，给自己划定一个小的资源库，在这个知识库的专属小资源库里，构建`实体`和`资源`之间的关系网。

4. `关系层`：这一层用于存储`实体`之间的关系

    实体之间的`关系`，也是一种知识，应当被存储，日后复用。

    可以在root文件夹下的`Wiki`子文件夹下的某个知识库文件夹(`Wiki_<知识库名>`)下的`.registry/human/`文件夹里打开`relationship_registry.md`查看，该知识库里的所有实体之间的关系。

5. `图谱层`：这一层用于存储不同`关系`的图。

    图结构可以快速关联知识，以免大范围搜索带来的开销和引起的AI注意力涣散

    光是关系代表的边即可构图，但不同的关系范围，可以构筑不同的图。

    这些图在不同的应用场景中会有不同的作用，比如对于推理性的任务，那些属于支撑、推导等正向关系的图显然更加重要，而对于审查任务，那些属于矛盾等反向关系的图则更重要。

    可以在root文件夹下的`Wiki`子文件夹下的某个知识库文件夹(`Wiki_<知识库名>`)下的`.registry/human/`文件夹里打开`knowledge_graph_registry.md`查看，该知识库里的所有已被构筑的图。

### 总结

| 五层架构 |
| --- |
| 图谱层 |
| 关系层 |
| 实体层/知识点层 |
| 资源层 |
| 文件层 |

总结的时候自顶向下看：

最顶层是属于`图谱层`的知识图谱，图的顶点是知识实体，图的边是两端顶点代表的知识实体之间的关系。知识图谱由某种关系属性所选定的边为基准进行绘制。

往下一层是属于`关系层`的关系，代表知识实体之间的关系，上层的图谱由该层的关系决定，可以通过`图谱`查找`关系`。

再往下一层是`实体层`，可以通过`关系`查找`实体`，尽管理论上应该是“图谱→关系→实体”这样的查找链，但为了提高查找速度，实际构建图谱时，把相应的实体直接链接到了图谱的节点上。

次底层`资源层`，可以通过`实体`查找对应的`资源`。

底层`文件层`，通过`资源`可以查找对应的`文件`。

这样，从顶层的图谱开始，可以一层一层追溯到底层的文件，层与层之间实现了封装与解耦，使得Valhalla系统可以按需加载所需的资料，也可以便于功能扩展(修改的影响仅限于本层)。

## 重新审视摄入操作

在教程01中，尝试了摄入操作，当时只是尝试使用了这一操作，并未了解背后发生了，这里将结合知识库系统的结构来具体说明这一操作的机制。

`摄入`操作的一般指令是`摄入<文件路径>`，输出是实体entity。

即`摄入`操作的输入在`文件层`，输出则是在`实体层`。

也就是说：**摄入操作跨越了知识库系统的三个层级**，是Valhalla系统中少见的跨层级操作。

需要注意的是：`摄入`操作不能从`文件层`直接跳跃到`实体层`，而是必须要通过`资源层`的操作。

`摄入`的大致操作流程如下：

1. 根据<文件路径>查找该文件是否已经在资源层注册，如果未在资源层注册，则先注册，获得唯一的`resource_id`，并在Library的`public_resources`进行备份。
2. 取得该文件`resource_id`后操作提升至`资源层`，在这里，会检查该资源是否位于目标知识库的`虚拟资料库`中。目标知识库就是当前启动的知识库，可以输入`当前状态`进行查看，`虚拟资料库`是该root中所有资源的一个子集，专门用于构筑`目标知识库`的`资源层`。如果该目标资源不在目标知识库的`虚拟资料库`中，则将该资源加入到目标知识库的`虚拟资料库`中。
3. 当确定该资源在目标知识库的虚拟资料库中后，说明该知识库的`资源层`构筑完毕，LLM将开始解读这份资源，提取出其中的知识实体，并登记保存到`实体层`。

# Valhalla 系统概览

Valhalla 是一个面向交叉学科研究团队的本地项目工作环境。
它以本地知识库为基础，以 skill 为运行载体，由 LLM 辅助维护和调用，使研究组成员能够持续贡献、共享、维护并转化跨学科知识，推进论文、实验、代码、综述、方案和工程任务。

## 核心理念

Valhalla 的设计建立在以下几个理念之上：

1. **从资料管理走向项目推进**

    Valhalla 不把知识库视为项目之外的附属资料夹，而是将其视为项目运行的基础环境。资料、知识点、关系、图谱和工作流共同构成 agent 的工作空间，使 agent 能够基于已有知识继续推进论文写作、实验设计、代码实现、综述整理、方案论证和工程维护。

2. **从孤立笔记走向结构化知识**

    Valhalla 不只是保存摘要或笔记，还要发掘和记录知识实体之间的语义关系。通过实体层和关系层，知识不再只是分散页面中的自然语言文本，而是逐步形成可以被检查、扩展、组合和调用的结构化知识网络。

3. **从静态知识库走向持久沉淀**

    Valhalla 不满足于在每次问答时临时检索资料片段，而是强调知识的长期沉淀。对话和使用agent也是知识，这些知识不应随着一次会话结束而消失，而是需要逐步积累为团队可复用的长期资产。

4. **对非计算机领域研究者友好**

    作为面向交叉学科研究人员的工具，系统应使非计算机出身的研究人员能够直接阅读和修改系统规则、工作流和服务逻辑，从而可以根据需要完成定制。

5. **可约束**

    系统在权限、状态等关键位置需要结构化约束，避免 LLM 在关键操作中自由发挥过度。

    Valhalla 通过状态、权限和风险等级约束 agent 的操作范围，使不同系统服务只能在合适的运行条件下被调用。

## 工程特点

Valhalla 以本地知识库为基础，以 skill 为运行载体，将资料组织、知识抽取、系统服务、任务工作流和项目推进能力整合到同一个可扩展环境中，使 agent 不只是访问知识，而是在知识环境中持续工作。

Valhalla 具有如下工程特点：

1. **面向 agent 的工作环境**

   Valhalla 的目标不是简单地保存资料或提供知识查询，而是为 agent 提供一个可以长期工作的项目环境。在这个环境中，agent 可以读取资料、理解知识库结构、调用系统服务、执行工作流，并基于已有知识持续推进论文、代码、实验、综述、方案和工程任务。

   因此，Valhalla 并不是一个被动的资料容器，而是一个能够支撑 agent 进行项目活动的工作基础设施。

2. **知识库系统与知识库管理系统分离**

   Valhalla 参考数据库系统的基本思想，将整体系统划分为“知识库系统”和“知识库管理系统”。

   `知识库系统`负责保存和组织项目知识，包括文件、资源、实体、关系和知识图谱。

   `知识库管理系统`则负责对知识库进行创建、登记、切换、摄入、检查、修复、调用和维护等操作。

   这种划分使 Valhalla 同时具备稳定的数据组织基础和可扩展的操作能力。知识库系统提供可持久保存的项目环境，知识库管理系统则使 agent 能够在该环境中执行具体工作。

3. **知识库系统独立于模型存在**

   Valhalla 的知识库系统由`本地文件夹`构建，其核心数据以文件、注册表、模板、表格和结构化文档的形式保存。因此，知识库本身不依赖特定模型存在。

   即使没有 LLM 参与，Valhalla 中的资料、资源、实体、关系和图谱仍然可以被保存、查看、迁移和维护。LLM 是 Valhalla 的运行时智能执行者，而不是知识库存在的前提。

4. **五层知识库体系结构**

   Valhalla 将知识库系统抽象为五层体系结构：`文件层`、`资源层`、`实体层`、`关系层`和`知识图谱层`。

   文件层允许使用者自由组织原始资料；资源层通过 `resource_id` 和公共副本机制，为底层文件建立稳定的抽象身份；实体层从资源中提取并维护知识点对象；关系层在 `.registry/machine/relationship_registry.yaml` 中记录带主体、客体、谓词和证据的实体关系事实；知识图谱层则根据不同任务和关系类型生成派生图谱视图，不另行创造关系事实。

   各层逐层提供服务、逐层封装实现。上层通过层间接口使用下层提供的能力，而下层不需要知道上层服务的具体实现。通过这种分层结构，Valhalla 将底层文件组织、资料身份管理、知识实体抽取、实体关系建模和图谱视图构建解耦，从而提高系统的稳定性、可维护性和可扩展性。

   在 Valhalla 中，一份原始资料文件通常会先被登记为资源，再被知识库引用、摄入为实体，并进一步形成关系和图谱视图，从而完成从资料到可调用知识的转化。

   Valhalla 强调知识的可追溯性。知识实体和关系不应脱离来源资料存在，而应尽可能保留其证据来源，以便后续检查、更新和纠错。

5. **参考混合内核架构的知识库管理系统**

   Valhalla 的知识库管理系统参考混合内核架构设计，可以视为一个建立在 skill 机制之上的轻量级项目操作系统。

   在这一抽象中，`LLM 被视为一个能力强大的 CPU`；`上下文窗口被视为内存`；`会话被视为进程`；`会话上下文被视为进程的内存空间`。

   通过这一结构，Valhalla 将 agent 的单次对话行为组织为可约束、可调度、可复用的项目工作过程。

6. **系统内核与系统服务分离**

    `混合内核架构简介`

        在操作系统设计中，内核负责维持系统运行所需的基本能力，例如进程管理、内存管理、权限控制、设备访问和系统调用等。围绕内核如何组织系统功能，通常可以区分出宏内核、微内核和混合内核等不同架构思想。

        宏内核倾向于将大量系统功能放在内核内部，使系统调用路径较短、执行效率较高，但也容易导致内核规模庞大、模块之间耦合较强。

        微内核则尽量缩小内核规模，只在内核中保留最基本的调度、通信和权限机制，将文件系统、驱动、网络等功能移到用户态服务中运行。这种方式模块边界清晰、可维护性较好，但服务之间通信和调度成本可能更高。

        混合内核可以理解为二者之间的折中。它并不追求把所有功能都放入内核，也不把所有服务都彻底移出内核，而是根据稳定性、性能、权限和维护需求，将核心机制保留在内核中，将可扩展、可替换、面向具体任务的功能组织为系统服务。这样既能保留内核运行秩序和关键控制能力，又能避免系统功能过度集中在一个庞大的核心中。

        Valhalla 借用了这种思想来组织知识库管理系统。系统内核只负责维持运行所必需的基础机制，例如启动自检、状态管理、路由加载、权限检查和操作约束；而资料登记、知识摄入、关系构建、图谱生成、黑名单管理、系统检查和项目推进等具体功能，则被设计为彼此解耦的系统服务。这样，Valhalla 既拥有一个稳定的运行核心，又允许各类服务根据研究场景不断扩展和替换。

   Valhalla 的知识库管理系统主要由`系统内核`和`系统服务`组成。

   `系统内核`负责维持系统运行状态、执行启动自检、加载路由、检查权限、验证状态约束，并维持基本运行秩序。

   `系统服务`则面向具体任务，直接操作知识库系统的不同层级，例如 root 管理、知识库创建、资料登记、知识摄入、关系构建、图谱生成、黑名单管理、系统检查和项目推进等。

   不同系统服务之间保持解耦。单个服务的修改不破坏其他服务，也不应影响知识库系统的整体结构。这使 Valhalla 可以在长期使用中逐步扩展，而不是依赖一次性设计完成全部功能。

7. **以自然语言为主体的系统构建方式**

   Valhalla 的主体由自然语言构建。系统的工作流、操作规则、服务说明、知识处理逻辑和项目推进流程主要通过自然语言描述，从而降低系统理解和修改门槛。

   同时，Valhalla 辅以少量结构化语言进行权限管理、状态约束、接口约定和数据校验，例如 contract、schema 等。只有在少数对稳定性和确定性要求极高的场景中，系统才使用 Python 脚本实现，例如启动自检、状态检查等关键操作。

   这种设计使 Valhalla 既保留自然语言系统的可读性和可定制性，又能在关键节点上获得结构化约束和工程稳定性。

8. **交叉学科研究人员的可定制设计**

   Valhalla 的设计初衷是服务交叉学科研究人员，尤其是需要管理复杂资料、构建团队知识库，并持续推进论文、实验、代码和项目工作的研究团队。

   自然语言构建方式、系统服务间解耦机制，以及知识库五层体系结构，使非计算机专业人士也能够理解 Valhalla 的运行逻辑，并根据自身研究场景对系统进行修改、扩展和定制。

   换言之，Valhalla 试图让研究团队不仅能够使用 agent，也能够塑造 agent 的工作环境。

9. **以 skill 为运行载体，直接参与项目推进**

   Valhalla 以 skill 作为主要运行载体。skill 不只是系统说明文档，也不是单纯的提示词集合，而是 Valhalla 进入 agent 工作过程的接口。

   通过 skill，Valhalla 可以将知识库结构、系统服务、权限约束、工作流和项目规则注入 agent 的工作上下文，使 agent 能够基于本地知识库直接参与项目推进。例如，agent 可以围绕已有资料进行知识摄入，基于实体和关系进行综述整理，调用项目工作流辅助论文写作，参考工程实体推进代码实现，或通过系统服务维护知识库结构。

   因此，Valhalla 的功能边界不止于知识库管理。它将本地知识库、系统服务和任务工作流组织在同一个 skill 体系中，使知识库从“存放知识的容器”转变为“agent 推进项目时的工作环境”。

## 知识库系统

知识库系统被抽象为5层体系结构

1. **第一层：文件层**

    文件层由原始文件组成。使用者可以根据需要自由组织这些资料文件，例如按照项目、人员、主题或时间进行分类。

    为防止系统自动操作底层文件造成不可控混乱，Valhalla 不在这一层提供直接修改原始文件组织方式的系统服务。文件层主要由使用者手动维护，系统只读取、识别和登记其中的资料。

2. **第二层：资源层/抽象资料层**

    资源层负责将文件层中的资料文件抽象为稳定的资源条目。一个 resource_id 表示一份内容与版本均唯一的信息对象。无论文件层中的文件如何组织、移动、改名或改变表现格式，resource_id 都是该唯一信息在 Valhalla 中的逻辑代表。

    resource_id 不等同于原始文件路径，也不等同于公共副本路径。它是上层系统引用资料时使用的稳定标识。

    同一 resource_id 可以包含 PDF、Markdown、TXT、OCR 或文本抽取等多个表现文件，每个表现文件又可以在 Library 的非公共文件夹中拥有多个来源副本。资源层为表现文件生成或绑定公共副本。上层结构只通过 resource_id 引用资料，再由资源层解析到适合读取的表现文件，从而避免直接依赖文件路径。

    `resource_registry.yaml` 是资源层机器权威注册表，`resource_registry.md` 是与它同步的人类可读投影。日常登记可增量更新 Markdown；名称、路径或状态发生批量漂移时，lint 只根据 YAML 校正 Markdown 投影。两者冲突时始终以 YAML 为准。

    资源注册表同时保存资源层派生反向索引：`usage.referenced_by` 记录哪些已登记知识库的哪些 entity 引用了该资源，`reference_count` 由这些反向引用计算而来。凡写入或更新 `entity_resource_map.yaml`、`entity_registry.yaml`，或改变已登记 active 知识库集合、知识库路径、目标 root 汇总状态的 operation，必须在同一 operation 内同步派生更新 `resource_registry.yaml` 与 `resource_registry.md` 的 usage；`sync_resource_usage` 只作为历史遗留清理、批量校正和手动维护入口。该反向索引不是 entity 主记录，也不得作为 entity_id 编号来源。

    这一层的作用是防止文件在使用、添加、删除过程中引起身份漂移。不同文件名、不同路径和不同格式可以表达同一信息；预印本、正式版、修订版或内容有实质增删的文件则必须使用不同 resource_id。资源层通过 resource_id、表现文件与公共副本机制，将上层知识结构与底层文件组织解耦。

3. **第三层：实体层/知识点层**

    在一个知识库通过虚拟资料库划定资源范围后，LLM 从该资料范围中的资料提取知识实体 entity。

    虚拟资料库不是新的物理文件集合，而是由若干 resource_id 组成的逻辑资料集合。它决定某个知识库可以使用哪些资料资源。

    每个知识库的 `local_resources`、`required_resources` 和 `excluded_resources` 均采用双轨文件：YAML 保存机器权威成员关系，Markdown 保存人类可读投影。YAML 同时保留用户加入时输入与成员状态；Markdown 展示加入时输入和资源层当前来源路径。只有 `membership_status: active` 的 YAML 条目参与虚拟资料库计算，`pending_removal` 条目立即失效并由 lint 在确认后批量清理。

    一个 resource_id 对应的资料可能提取出多个 entity；同一个 entity 也可能来自多个 resource_id。每个 entity 都拥有唯一的 `entity_id`。

    `entity_id` 是知识库本地编号。新 entity 的编号只能根据当前知识库的 `.registry/machine/entity_registry.yaml` 和 `entities/ent_*.md` 计算，不得根据其他知识库或 `resource_registry.yaml` 中的历史 usage 推导。

    在 Valhalla 中，entity 不只是关键词或标签，而是一个经过整理的知识点对象。它通常对应一个可持续扩展的内容文件，用于记录该知识点的定义、解释、来源、证据和后续补充。

4. **第四层：关系层**

    关系层用于表示一个知识库中各个 entity 之间的关系。关系可以被分类，以表达不同类型的语义连接，例如支撑、矛盾、包含、依赖、因果、对比、等价、扩展等。

    关系层的作用不是简单地把实体连起来，而是记录知识点之间的可解释结构，使系统能够进一步组织、检查和推理知识。

5. **第五层：知识图谱层**

    知识图谱层基于实体层和关系层构建知识图谱。它可以根据不同任务、主题或关系类型，生成不同用途的图谱结构。

    因此，知识图谱层不是保存唯一固定图谱，而是提供面向不同使用场景的图谱视图。例如，可以基于支撑关系构建证据图谱，基于矛盾关系构建争议图谱，基于因果关系构建机制图谱，或基于项目需求构建任务图谱。

    比如：在推进任务时，可以使用“支撑+包含+依赖+因果+等价”的知识图谱。
    而在审核任务成果时，就可以使用“矛盾+对比”的知识图谱。

## 知识库管理系统

Valhalla 的知识库管理系统参考了混合内核操作系统架构，用于组织 agent 对知识库系统的各类操作。它并不是传统意义上的底层操作系统，而是一个建立在 skill 机制之上的轻量级运行环境，用于维持 Valhalla 的基本运行秩序，并调度各类系统服务。

在该架构中，`SKILL.md` 被视为 Valhalla 的`系统内核`。每次启动 Valhalla 时，`SKILL.md` 都会被加载，因此它承担系统运行所需的基础职责。目前，系统内核主要实现三类功能：启动自检、安全约束和指令路由。启动自检用于确认 Valhalla 的基本结构和运行条件；安全约束用于限制高风险操作；指令路由 `router` 则负责将用户输入分发到相应的系统服务入口。

`系统服务`采用统一的执行流程：

    ```text
    router → contract → workflow
    ```

其中，`router` 负责对用户输入的 prompt 进行分类，判断其对应的操作类型，并加载相应的 `contract` 文件。

`contract` 是系统服务的资格验证模块。它负责检查当前系统状态、权限约束、风险等级和必要条件，判断该操作是否允许执行。只有当 `contract` 验证通过后，系统才会继续加载对应的 `workflow` 文件。

`workflow` 则定义系统服务的具体操作流程。它描述在验证通过后，agent 应该如何执行该服务，包括读取哪些文件、修改哪些结构、生成哪些结果，以及如何向用户汇报执行情况。

因此，Valhalla 的系统服务并不是直接由 prompt 触发执行，而是经过一条明确的受控路径：

    ```text
    分类 → 验证 → 实施
    ```

这种设计使 Valhalla 在保持自然语言工作流灵活性的同时，也能够在关键操作前加入状态检查、权限约束和风险控制，从而降低 agent 自由发挥导致系统结构混乱的风险。

## 现有缺陷与未来改进

### 现有缺陷

尽管 Valhalla 的目标是成为面向交叉学科研究团队的 agent 工作环境，但当前版本仍处于早期原型阶段，存在若干限制。

1. **尚未实现远程协作能力**

   Valhalla 当前主要基于本地文件系统运行，尚未实现远程访问、多人在线协作和分布式同步功能。因此，在团队使用场景下，目前更适合部署在一台专用计算机上，由研究组成员轮流使用，或通过共享工作站进行集中维护。

   尚未实现并发写入和冲突解决机制，因此当前更适合单人或轮流使用，不适合多个成员或多个 agent 同时修改同一知识库

2. **缺少针对知识库文件夹的权限保护机制**

   Valhalla 的核心数据保存在本地知识库文件夹中，包括资料文件、资源注册表、实体文件、关系表和图谱文件等。目前系统尚未对该文件夹实现细粒度安全防护，例如不同成员的访问权限、写入权限、删除权限和操作审计等。

   因此，在多人使用场景下，Valhalla 仍需要依赖操作系统、版本管理工具或人工规范来避免误删、误改和越权操作。

3. **尚未实现备份与回滚机制**

   Valhalla 当前尚未实现完整的自动备份、版本快照和回滚机制。由于系统服务会直接修改本地知识库文件，例如注册表、实体文件、关系表、图谱文件和日志文件，一旦发生误操作、错误摄入、错误修复或文件结构破坏，系统暂时无法自动恢复到修改前状态。

   这一问题在 agent 工作环境中尤其重要。因为 agent 可以连续执行多步操作，单次错误可能扩散到多个文件，导致知识库结构出现连锁性问题。因此，未来需要为 Valhalla 增加操作前快照、增量备份、修改日志、差异对比和回滚恢复机制，使高风险操作具备可撤销性。

4. **尚未实现上下文调度机制**

   Valhalla 当前尚未实现完整的上下文调度能力。系统在运行过程中加载的部分文件或工作流内容，一旦进入 prompt，就难以被主动移出上下文窗口。这会导致长任务中上下文占用持续增加，进而影响后续操作的稳定性和可扩展性。

   未来需要引入更明确的上下文加载、暂存、压缩和换出机制，以提高系统在复杂任务中的持续工作能力。

### 未来改进

尽管存在上述限制，当前版本的 Valhalla 已经具备基本可用性。

它已经实现了本地知识库组织、五层知识库结构、系统内核、系统服务、路由、契约验证和工作流执行等核心机制，能够支持资料登记、知识摄入、实体维护、关系构建、图谱组织和项目推进等基本任务。

Valhalla 的分层与解耦设计为后续演进提供了较好的扩展基础。未来可以在不破坏现有知识库结构的前提下，逐步补充新的系统能力。

1. 可以加入远程同步模块，以支持团队成员在不同设备上协作使用 Valhalla。

2. 可以加入权限管理模块，对知识库文件夹、系统服务和高风险操作进行更细粒度的访问控制。

3. 可以加入备份与回滚模块，在执行写操作前自动生成快照，并记录文件修改差异，使错误操作能够被追踪和撤销。

4. 还可以加入上下文调度模块，用于管理 prompt 中的运行时内容，实现加载、暂存、压缩和换出。

因此，Valhalla 当前的不足主要是工程实现阶段的功能缺口，而不是整体架构上的根本限制。随着远程协作、权限管理、备份回滚、版本控制和上下文调度等模块逐步加入，Valhalla 可以从单机可用的本地项目工作环境，进一步演化为支持团队协作的 agent 工作平台。
